## 1. 已确定的目标与本阶段边界

- 两个手柄硬件相同；当前 `xuexi` 与用户复制的 `备份` 是不同文件夹中的左右独立工程，分别维护。
- 分开：各自运行菜单、摇杆、按键、陀螺仪、OLED 和无线功能，各自控制绑定的接收端。
- 合体：右侧通过串口上传输入；左侧负责统一状态和控制发送；两块 OLED 显示同一份业务信息。
- 左手柄单机进入 MW/JS 后，X/Y 输出横移和前后速度，Z=0；双手柄时由右摇杆 X 提供 Z，右手柄 PA8 `Key_UP` 切换自转使能。左侧四键负责导航和进入模式；右侧 U/D/L/R 在双手柄 MW/JS 控制页按住时分别辅助前进/后退/左移/右移，不再参与左侧菜单。
- `MW/GYRO` 菜单保留为预留项，目前禁止控制使能，不产生控制命令。
- 2.4G 帧长仍为 16 字节，帧头/帧尾和底层驱动不变；模式编号 0/1/2 不变，原未使用的 `mode=3` 改作 MW。MW 中 byte7=`x`（正值向右）、byte8=`y`（正值向前）、byte14=`z`（正值俯视逆时针），均为有符号 `int8` 百分比，范围 -100～100；左手柄单机时 `z=0`，其余 MW 命令字段为 0。
- 共同配置、输入快照、任务调度、串口/CRC、固定角色、合体职责、OLED 同步和无线发送交接已写入两份工程。
- 接收端需继续按 16 字节原样转发；小车端应把 `mode=3` 按上述 MW 字段解释。小车端解析、超时停机和麦轮运动学尚未实现。

两个工程分别保存源码、Keil工程、构建目录和日志：`xuexi` 是 LEFT，`备份` 是 RIGHT。两边各自编译；修改共用协议时手动同步定义，不使用共享源码链接或同一工程的多目标代替独立工程。

### 第 4 步：实现合体状态机（已完成代码实现）

两边各自新增 `hardware/controller_mode.c/.h`，由原有 `CTRLTASK` 每 5 ms 更新；不另建 FreeRTOS 任务。

四个状态：

| 状态 | 含义 | 目标行为 |
|---|---|---|
| SOLO | 已确认分开 | 各自运行独立功能 |
| CONNECTING | 合体触点有效，正在确认链路 | 关闭控制，确认双方身份与状态 |
| DUAL | 双向链路已确认 | 进入合体业务状态 |
| FAULT | 触点仍合体，但链路失效或双方不一致 | 控制保持关闭，等待恢复或确认拆开 |

操作：

1. 在两个工程分别接入正式HELLO、HELLO_ACK、HEARTBEAT：携带固定左右身份、协议版本和连接编号，拒绝同角色或不兼容版本；关闭共同测试入口。
2. 上电主动读取合体触点，之后周期读取并消抖；不能只等插拔 EXTI。
3. 原 `DoubleModle` 可暂时用于显示适配，但不能代替完整连接状态。
4. 初值建议：触点稳定确认 30 ms，心跳 20 ms，通信超时 100 ms；这些是待实测调整的配置值。
5. 双方互相确认后才能进入 DUAL，不能只凭单方向收到了一个包。
6. 状态变化时清理按键边沿和旧事件，避免合体时一直按着的键被当作新点击。
7. 状态可从 `ControllerMode_GetSnapshot` 和链路诊断读取；屏幕/变量实机观察待上板。无线交接仍由第 7 步处理。

验收：

- [x] 固定角色、双向身份确认、接触消抖、心跳超时和状态切换的软件逻辑已实现并构建通过。
- [ ] 分开上电、合体上电、运行时插拔均进入正确状态。
- [ ] 合体触点抖动不会反复进入退出。
- [ ] 合体时一侧掉电、单方向 UART 断线能进入故障状态。

### 第 7 步：交接无线发送职责，保留旧协议（已完成代码实现）

本步可改旧协议之外的业务许可和队列消费逻辑，**不改旧帧布局及字段含义**。

操作：

1. 为无线任务增加显式发送许可：独立发送、合体主侧发送、禁止控制发送。
2. 合体开始时，双方先关闭控制；右侧按当前旧模式生成停止命令，发送给自己的接收端后退出控制发送并通知左侧。
3. 右侧完成旧模式停止帧后，在心跳载荷中置位停止确认；左侧收到确认后才开放控制与无线发送许可。合体时仅左侧可以发送运动命令。
4. 本阶段左侧仍可发送原来已有的 SP/RA 命令；右侧输入先用于同步显示和测试，不能擅自映射成旧协议中的麦轮通道。
5. 停机按当前模式语义处理：SP 速度归零；RA 停速度并按原逻辑处理目标。不要不分模式将所有目标字段清零。

## 6. F103 性能、任务优先级与 CRC 延迟规划

本节保留性能测量目标和验收要求。任务优先级、控制周期和链路缓冲配置已在左右共同代码中实现；左右工程已分别复制，仍需各自构建并记录 CRC 耗时、控制抖动、堆栈水位等实测数据，尤其关注承担统一控制与无线发送的左侧。

### 7.1 当前基线与主要风险

当前时钟配置为外部 8 MHz、PLL ×9，即按 72 MHz 运行；工程链接配置的 RAM 上限为 20 KiB。硬件能力参考 [ST STM32F103x8/xB 数据手册](https://www.st.com/resource/en/datasheet/stm32f103rb.pdf)。

编写时核对的代码情况：

- `Core/Src/freertos.c:62` 和 `:169`：OLED 与五个用户任务目前都使用 `osPriorityNormal`，即数值 24。
- `Core/Inc/FreeRTOSConfig.h:70`：RTOS tick 为 1 kHz；`:71` 最大优先级数为 56；`:73` 堆大小为 10,240 字节；`:90` 定时器服务任务优先级为 30。
- `hardware/TASK.c:435`：摇杆累计十次、每次间隔 5 ms，约 50 ms 发布一次。更快的串口发包不等于更快的新输入。
- `hardware/fun.c:80` 等输入接收处可能等待 100 ms；`hardware/TASK.c:366` 的无线队列接收使用无限等待。提高优先级不能消除阻塞等待。
- OLED 使用 400 kHz I2C，较长数据块通过 DMA 发送；DMA 降低 CPU 搬运负担，但不会缩短总线自身的传输时间，绘图仍有 CPU 开销。

因此，先解决输入更新、等待方式和显示优先级，再依据实测判断是否需要优化 CRC。

### 7.2 只新增一个串口链路任务

状态机、输入映射、协议和 UI 同步是代码模块，不需要分别创建任务：

| 业务 | 执行位置 |
|---|---|
| UART 收包、CRC、握手、心跳、协议解析 | 新增的串口链路任务 |
| 模式决策、输入超时、控制映射、生成命令 | 现有 `CTRLTASK` |
| 摇杆/姿态采集与发布快照 | 现有 `JSTask`、`GYROTask` |
| 按键采集与事件生成 | 现有 `KEYTASK` |
| 无线发送许可检查与发包 | 现有 `FREQ2_4GTask` |
| 绘图、动画、OLED 传输 | 现有显示任务 |

串口任务以通知/事件唤醒，等待时允许超时检查和发送调度。每次处理有上限，解析完有限数量的帧后检查期限；不能因持续输入而一直占用 CPU。CRC 不单独建任务。

### 7.3 建议优先级和周期

沿用当前 56 个优先级配置，先采用下面的初始数值，不需要额外增加优先级数量。FreeRTOS 任务数字越大，优先级越高。

| 任务 | 建议数值 | 运行方式与职责 |
|---|---:|---|
| 串口链路任务 | 26 | 收包唤醒，有限长度解析与 CRC；输入帧先按 10 ms 上报，心跳按 20 ms |
| `CTRLTASK` | 25 | 5 ms 绝对周期，读最新快照，检查停止/超时，不等新输入到达 |
| `JSTask`、`GYROTask` | 24 | 保留当前采集方式作为基线，单独评估采样与滤波延迟 |
| `FREQ2_4GTask` | 23 | 保留旧协议；按当前发送需求运行并及时检查许可/停止状态 |
| `KEYTASK` | 20 | 事件唤醒，处理后阻塞；避免无延时轮询 |
| OLED 显示任务 | 8 | 显示可被控制抢占；实时数值同步先按 50 ms，动画沿用现有时间轴 |
| 软件定时器服务任务 | 当前 30 | 可先保留；回调只做短操作，不 CRC、不绘图、不阻塞发送 |

这些优先级是待验证方案，不是实时性证明。若姿态计算或通信解析耗时过大，应缩减单次工作或调整周期，不能无限提高优先级。

执行要求：

1. 控制周期用 `vTaskDelayUntil`；在任务中只读取最新一致快照，不用 100 ms 等待维持一个名义 5 ms 周期。
2. 无线任务使用通知或有界等待响应许可变化，清理旧待发数据。SPI 轮询传输需要明确最坏耗时与错误退出，不依赖无限忙等。
3. 停止请求不能排在长菜单/动画处理后面；发布短事件或停止标志，在控制周期优先处理，并测量从按键到失能的实际延迟。
4. 页面状态只提交给 OLED 任务，控制和串口任务不直接执行绘图/I2C 等待。
5. 不在关中断、暂停调度或长临界区内计算 CRC、绘图、发送；快照复制的保护范围尽量短。
6. 优先级常量统一管理，分清 CMSIS 枚举和原生 FreeRTOS 数值；当前 `osPriorityNormal` 为 24，不能随意改成 3 后认为其他任务仍处于同一优先级体系。

### 7.4 任务优先级与中断优先级分开

任务：数字越大越优先；Cortex-M NVIC：数字越小越优先。这是两套不同的设置。

当前 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY=5`。会调用 `...FromISR` 的 UART/DMA 等中断，在当前配置下 NVIC 优先级数值须为 5～15，不能为了“更快”设成 0～4 后继续调用 RTOS API。新增串口中断可先按 5 配置，最终核对优先级分组与其他中断。

中断只接收/搬运数据、记录状态和唤醒任务；需要时使用 `portYIELD_FROM_ISR` 让被唤醒的高优先级任务及时运行。完整帧 CRC 和业务判断放在任务中。

若涉及 `.ioc` 的 DMA/中断配置，先确认再修改，生成代码只在允许区域接入用户逻辑。参考 [FreeRTOS Cortex-M 中断优先级说明](https://www.freertos.org/FreeRTOS_Support_Forum_Archive/November_2012/freertos_NVIC_priority_and_FreeRTOS_priority_6237079.html)。

### 7.5 CRC16 的计算和线路延迟

本节 CRC16 只针对新增的手柄串口协议，不向当前 2.4G 帧追加 CRC。

115200 波特率、8N1 时，每个字节包含 10 个线路位，理论线路时间为 `字节数 × 10 / 115200`：

| 情况 | 理论线路耗时 |
|---|---:|
| 32 字节完整帧，含协议头和校验 | 约 2.78 ms |
| 增加 2 字节 CRC16 的增量 | 约 0.174 ms |
| 40 字节完整帧 | 约 3.47 ms |

以上不含 CPU 计算、调度等待和排队。32 字节完整帧若每 10 ms 发送一次，单方向线路占用约 27.8%；重发、心跳和显示同步还需要计入各自方向的预算。全双工两方向分别统计，并为突发消息留余量。

建议实现：

- CRC16 使用 256 项查表，表为 `static const uint16_t`，共 512 字节；链接到 Flash/RO 区，并在 map 中确认没有复制到 RAM。
- 对完整有效长度的帧计算，不对整个接收缓冲或已经检查的历史数据反复计算。
- 长度合法再做 CRC，校验通过才更新输入状态；CRC 错误直接丢弃并计数。
- 同时统一多项式、初值、反射、结果异或和字节序，使用标准测试向量验证两侧实现。
- 可以先采用“32 字节校验最大耗时不超过 50 μs”作为初始验收目标；**这是目标，尚未实测，不是 F103 的性能保证。**
- DWT 记录函数耗时与受到抢占后的完成时间，必要时分别统计纯计算和系统负载下的延迟；不为了测量而长时间关闭中断。

不凭估计删除 CRC。若实际超过预算，再比较编译优化、查表法、增量计算和帧长度，先确认瓶颈所在。

### 7.6 RAM 预算与栈检查

2026-10-10 17:45:46 的旧构建显示 RAM（RW+ZI）18,080 字节。双手柄第 1～7 步软件实现后的 2026-10-11 Keil 构建结果为：LEFT `Code=46184, RO-data=2632, RW-data=488, ZI-data=18176`，`RW+ZI=18664/20480`，静态余量 1816 字节；RIGHT `Code=46184, RO-data=2632, RW-data=480, ZI-data=18176`，`RW+ZI=18656/20480`，静态余量 1824 字节。两者都包含 10,240 字节 FreeRTOS 堆；这些是链接期静态数据，不代表运行时堆余量或任务栈水位，后两项仍待板上读取。

内存预算规则：

1. 新任务的动态栈和 TCB 从已有 RTOS 堆中分配，消耗堆内部余量；不能把整个堆和动态任务栈再重复相加。
2. 新增静态 UART 缓冲和输入快照会直接增加 map 中 RW/ZI。当前链接区域余量与 RTOS 堆剩余量分别检查。
3. 原生 `xTaskCreate` 栈参数以 word 为单位，F103 上 256 words 为 1 KiB；CMSIS `stack_size` 以字节为单位，不能混淆。
4. 链路任务栈先依据函数局部变量和实际调用深度预算；测量栈水位后调整，不能直接照搬一个未经验证的大小。
5. 先规划一个固定 RX 环形缓冲、一个有界 TX 缓冲及少量快照；例如 128 字节 RX 是初步候选，要根据最坏解析间隔和最大帧长度计算。115200 下连续接收约 11.1 ms 即可填满 128 字节，必须检测溢出。
6. 不新增整屏 OLED 同步缓冲、长历史队列和大数组局部变量；DMA TX 缓冲在传输完成/中止前保持有效且不可覆盖。
7. 不默认增大 10 KiB 堆；先读取堆剩余量、最低剩余量和各任务最小栈余量，再决定是否调整。

诊断使用 `xPortGetFreeHeapSize()`、`xPortGetMinimumEverFreeHeapSize()`、`uxTaskGetStackHighWaterMark()`。栈水位单位为 word，换算字节后记录；保留栈溢出检测。参考 [FreeRTOS 堆管理说明](https://www.freertos.org/Documentation/02-Kernel/02-Kernel-features/09-Memory-management/01-Memory-management)。

建议记录的性能变量：CRC 当前/最大耗时、链路解析最大耗时、控制周期最大执行时间和最大启动偏差、输入最大年龄、无线实际发送间隔、UART 溢出计数、堆最低剩余量、各任务最小栈余量。

总响应时间包含：采样/滤波等待 + 等待上报 + 串口线路 + 解析/调度 + 控制调度 + 无线发送与接收端处理。CRC 只是其中一项；保持当前 50 ms 摇杆发布方式时，应明确这个限制，不能宣称系统已经达到 5 ms 输入响应。

压力场景至少包括：两侧持续输入、连续 OLED 页面动画、重复按键、单方向断线、错误/连续串口帧、无线失败、连接状态变化，以及长时间运行。每次检查周期超期次数、丢包/溢出、故障响应和内存水位；最坏运行时间需要通过测量建立预算。

采样优化应作为独立小步骤：先记录当前手感与延迟，再决定是否缩短平均窗口或更换滤波方法，分别验证噪声和响应；不与工程拆分一起修改。
